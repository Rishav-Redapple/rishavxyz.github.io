# V8 Engine: JavaScript Memory and Garbage Collection

High-level languages like JavaScript manage memory automatically. The runtime engine allocates memory when code creates objects, arrays, and strings. When values lose their references, the Garbage Collector (GC) reclaims system memory.

Treating garbage collection as an unknown process creates stability risks. Long-running Node.js services and complex web applications can develop memory issues. Inefficient memory usage leads to latency spikes, thread freezes, and process crashes.

The V8 engine powers Google Chrome, Node.js, Bun, and Deno. This document explains how V8 allocates memory and runs garbage collection.

---

## 1. The V8 Memory Layout

V8 divides runtime memory into two primary areas: the **Stack** and the **Heap**:

- **Stack:** Stores primitive values (numbers, booleans, small strings) and pointers referencing heap objects. The CPU manages stack frames through push and pop operations.
- **Heap:** A contiguous segment of virtual memory for reference types (objects, arrays, closures, compiled functions, and dynamic strings).

The V8 Heap contains several specialized spaces:

1. **New Space (Young Generation):** Where newly created objects begin their lifecycle. This space is small (typically 1MB to 64MB). It supports fast allocations and collections.
2. **Old Space (Old Generation):** Holds long-lived objects that survived minor GC cycles. Old Space is divided into:
   - _Old Pointer Space:_ Stores objects with references to other objects.
   - _Old Data Space:_ Stores objects containing raw payload data (strings, boxed numbers, byte buffers).
3. **Large Object Space:** Holds objects exceeding standard allocation size limits (such as large arrays or buffers).
4. **Code Space:** Stores native machine instructions generated by the TurboFan compiler.
5. **Map Space:** Stores hidden classes (Shapes) that track object structures for fast property lookups.

---

## 2. The Generational Hypothesis

V8's memory management relies on the **Weak Generational Hypothesis**:

> _"Most objects die young."_

Most runtime allocations have short lifespans. Examples include loop variables, function arguments, intermediate promises, and temporary strings. These objects become unreachable milliseconds after creation.

V8 divides the heap into Young and Old generations. This structure avoids scanning long-lived objects during routine cleanup. V8 runs an ultra-fast **Minor GC** over the small Young generation frequently. It executes a comprehensive **Major GC** over the Old generation less often.

---

## 3. Minor GC: The Scavenger

The Young generation consists of two equal semi-spaces: **From-Space** (active allocation area) and **To-Space** (compaction target during collection).

### Allocation Pointer Bump

Allocating memory in From-Space uses an `allocation_top` pointer. When code creates an object (`const item = {}`), V8 advances the pointer by the object byte size. Allocation speed matches standard stack assignment.

### The Scavenge Step

When From-Space becomes full, V8 triggers a **Scavenger** pass:

1. The collector scans root pointers (the active execution stack and global objects) to find reachable objects in From-Space.
2. Reachable objects are copied contiguously into To-Space. This copy eliminates memory fragmentation without a separate compaction phase.
3. Unreachable objects are omitted.
4. From-Space and To-Space swap roles.

### Object Promotion

Objects that survive one scavenge pass receive an intermediate marker. If an object survives a second scavenge cycle, V8 promotes it to **Old Space**.

---

## 4. Major GC: Mark-Sweep-Compact

When Old Space reaches internal memory limits, V8 triggers a Major GC. This process executes the **Mark-Sweep-Compact** algorithm.

### Phase 1: Tri-Color Marking

V8 tracks object reachability using three states:

- **White:** Unvisited objects. All objects start as white. Objects that remain white after marking are collected.
- **Grey:** Discovered objects whose referenced children are not yet evaluated.
- **Black:** Evaluated objects whose child references have been added to the marking stack.

The marking cycle:

1. V8 identifies root pointers (execution stack frames, global scope, DOM handles).
2. Root objects move to the grey marking stack.
3. The collector takes an object from the grey stack. It marks referenced objects as grey and marks the parent object black.
4. The process repeats until the grey stack is empty.

### Phase 2: Sweeping

V8 inspects memory pages in Old Space. It records contiguous blocks of dead (white) memory in **Free Lists**. Free lists group memory blocks by size categories for future allocations.

### Phase 3: Compacting

Old Space fragments over time. Small surviving objects become surrounded by free blocks. During compaction, V8 slides surviving objects toward the start of each page and updates all references.

## 5. Orinoco: Reducing Stop-The-World Pauses

Garbage collection historically required a **Stop-The-World (STW)** pause. The runtime suspended the main JavaScript thread during heap traversal. A 100ms GC pause caused dropped frames in 60 FPS interfaces (which have a 16.6ms frame budget).

Project **Orinoco** introduced concurrent and parallel collection mechanisms:

1. **Parallel Marking and Sweeping:** Background worker threads assist the main thread during collection passes.
2. **Incremental Marking:** V8 divides marking work into small time slices (5ms to 10ms) between normal JavaScript execution loops.
3. **Concurrent Marking:** Background threads mark objects while JavaScript mutates the heap.
4. **Idle-Time GC:** V8 coordinates with the event loop. The runtime executes small GC tasks when idle frames occur.

## 6. JavaScript Memory Leaks

Unused memory is collected only when code removes all references. Objects connected to a root pointer cannot be freed by V8.

### 1. Accidental Closure Retention

Closures retain their enclosing lexical scope. An inner function holds its outer variables in memory:

```typescript
// ❌ LEAK PATTERN: The interval holds outerLargeData in memory indefinitely
function startService() {
  const outerLargeData = new Uint8Array(50 * 1024 * 1024) // 50MB buffer

  return function logStatus() {
    console.log('Service active')
    // Even though outerLargeData is never referenced here,
    // some engines retain the whole lexical scope record!
  }
}

const reporter = startService()
setInterval(reporter, 1000)
```

Separating lexical scopes prevents large temporary buffers from remaining in memory:

```typescript
// ✅ FIX: Clean scope boundaries
function startServiceClean() {
  {
    const outerLargeData = new Uint8Array(50 * 1024 * 1024)
    processBuffer(outerLargeData)
  } // outerLargeData falls out of block scope here

  return function logStatus() {
    console.log('Service active')
  }
}
```

### 2. Unbounded Collections and `WeakMap`

Standard `Map` and `Set` collections hold strong references. Cached keys and values remain in memory indefinitely:

```typescript
// ❌ LEAK: Every cached session stays alive forever
const userCache = new Map<HTMLElement, UserData>()

function trackUserElement(element: HTMLElement, data: UserData) {
  userCache.set(element, data)
}
// When element is removed from DOM, userCache still retains it!
```

A `WeakMap` holds weak references to objects. When no other strong reference exists, V8 collects both key and value:

```typescript
// ✅ FIX: WeakMap allows garbage collection when DOM element is unmounted
const userCache = new WeakMap<HTMLElement, UserData>()

function trackUserElementSafe(element: HTMLElement, data: UserData) {
  userCache.set(element, data)
}
```

### 3. Lingering Event Listeners and Timers

Persistent intervals and event handlers maintain active references to attached objects:

```typescript
// Clean teardown pattern
class WebSocketMonitor {
  private timer: NodeJS.Timeout | null = null

  public connect() {
    this.timer = setInterval(() => this.heartbeat(), 5000)
  }

  public destroy() {
    if (this.timer) {
      clearInterval(this.timer)
      this.timer = null
    }
  }
}
```

## 7. Diagnosing Leaks with Chrome DevTools

Memory leak inspection in Chrome DevTools uses the following workflow:

1. Open **Chrome DevTools** and select the **Memory** tab.
2. Capture a baseline **Heap Snapshot**.
3. Execute the suspected application action multiple times.
4. Capture a second **Heap Snapshot**.
5. Switch the view from **Summary** to **Comparison** and sort by **Size Delta**.
6. Inspect the **Retainers** tree to find the root pointer preventing object collection.

The relationship between the Young generation scavenger and Old generation mark-sweep explains runtime performance and memory usage in V8.
